# Git 工作流

一套贯穿"新需求 → 分支开发 → 推送与合并确认"的 git 工作流。核心是**三个必须询问用户的决策点**：

1. **开发前**：检测到新需求、即将改动代码时 → 询问用户是否创建新分支；
2. **推送前**：任何 `git push`（特性分支、合并后的主干）之前 → 询问用户是否推送；
3. **开发完成后**：询问用户是否合并回主干。

> 为什么：主干应该始终处于可发布状态，远程历史一旦推送就会影响他人。把每个需求放到独立分支开发，推送和合并都经用户确认后再执行，既能隔离半成品，也让"推送/合并"成为显式的、用户知情同意的动作。你的职责是**提出**这些问题并执行用户的决定，而不是替用户做决定。本地提交（commit）发生在自己的分支上、随时可改，不需要问；但 push 会把改动送到共享的远程，**必须先问**。

## 触发条件

满足以下任一情况，就遵循本工作流：

- 用户提出需要**修改代码/文件**的新需求：新功能、Bug 修复、重构、性能优化、文档改动、配置改动等；
- 用户提到 git 相关概念：分支、合并、主干、提交、commit、PR、push、rebase 等；
- 用户要求"开始开发 / 实现 / 改一下 / 加一个…"且实现会改变 tracked 文件。

**不触发**：纯问答、只读分析、用户明确说"不用管 git / 我自己管理"。

## 工作流总览

```
[新需求出现]
   │
   ├─ 用户明确跳过 git？──────────────► 直接干活，不再问
   │
   ▼
[决策点 1：是否创建新分支]（动手改任何文件之前）
   │
   ├─ 在主干 → 询问用户（见下）
   ├─ 已在特性分支 → 说明并继续，不重复询问
   └─ 用户选择"当前分支直接改/跳过" → 按用户选择执行
   │
   ▼
[分支上开发 + 按仓库风格提交]（本地提交，无需询问）
   │
   ▼
[需要 push 的时刻]（开发完成、或用户要求推送、或创建 PR）
   │
   ▼
[决策点 2：是否推送分支]（任何 git push 之前，必问）
   │
   ├─ 无远程 → 说明并跳过推送
   ├─ 用户选择"推送" → 执行 push
   └─ 用户选择"暂不推送" → 改动只保留在本地分支
   │
   ▼
[完成判定]：实现完成 +（可行时）测试通过 + 改动已提交、工作区干净
   │
   ▼
[决策点 3：是否合并回主干]（完成时）
   │
   ├─ 合并 → 按合并流程执行
   ├─ 创建 PR → 仅在用户同意且存在远程时
   └─ 暂不合并 → 报告分支状态与后续如何继续
```

## 决策点 1：是否创建新分支（动手改代码之前，必问）

在修改任何文件**之前**，按顺序检查：

1. **是否 git 仓库**：`git rev-parse --is-inside-work-tree`。不是 → 告知用户当前目录不是 git 仓库，询问是否 `git init`（若同意：init 后如尚无提交，先做一次初始提交，以便存在主干分支）。
2. **当前分支**：`git branch --show-current`。
   - 输出为空且处于 detached HEAD → 提示用户，先 `git switch <主干>` 回到主干再继续。
3. **工作区是否干净**：`git status --short`。
   - 有未提交改动 → 提示用户，询问是**先提交**还是 **stash** 再开分支（推荐 stash 保持主干干净；或按用户意愿提交到当前分支）。
4. **分支判断**：
   - 已在特性分支（非主干）→ 告知用户"当前在分支 X，本次需求直接在该分支开发"，继续，**不再询问**。
   - 在主干（main/master，检测方法见命令速查）→ **必须用 ask_user_question 询问**：

> **检测到新需求：「<一句话概括需求>」。是否创建新分支来开发？**
> - 创建新分支（推荐）——建议分支名：`<feat|fix|refactor>/<kebab-case-简写>`
> - 在当前分支直接改（不建分支）
> - 跳过 git 流程，我自己管理

询问时把推荐项放在第一个并标注"推荐"。用户选"创建"后：

- 分支名：`<类型>/<kebab-case-slug>`，类型取 `feat`（新功能）/ `fix`（修复）/ `refactor` / `docs` / `chore`，slug 用需求摘要生成（跟随仓库已有命名风格，先 `git branch -a` 看看）。
- 执行：`git switch -c <分支名>`（旧版 git 用 `git checkout -b <分支名>`）。
- 建好后告知用户当前在哪个分支，再开始开发。

## 开发中守则

- **所有修改只发生在当前分支上**；不在主干上直接修改或提交。
- 提交前 `git status` / `git diff` 复核改动范围，只 `git add` 本需求相关的文件。
- **提交信息**：遵循仓库既有风格（先看 `git log --oneline -10`）；无特殊风格时用 Conventional Commits：`<type>(<scope>): <摘要>`，如 `feat(auth): 支持邮箱登录`、`fix: 修复登录空指针`。一条提交只包含一个逻辑单元；说明做了什么和为什么。
- **push 必须先问**：任何 `git push`（特性分支、合并后的主干）之前，都必须先走「决策点 2」征得用户明确同意。**"完成""好的""就这样"等日常对话不算同意**，只有用户显式选择了"推送"或"创建 PR"选项才算。没有配置远程时跳过，不报错。
- 避免把无关文件带进提交。

## 决策点 2：是否推送分支（任何 push 之前，必问）

在开发完成、或用户要求推送、或即将创建 PR 等任何需要 `git push` 的时刻，先检查再询问：

1. **是否配置了远程**：`git remote -v`。没有 → 告知用户"仓库未配置远程，跳过推送"，继续后续流程（本地提交不受影响）。
2. 有远程 → 在 push **之前**用 ask_user_question 询问：

> **分支 `<分支名>` 的改动已提交。是否推送到远程仓库？**
> - 推送到远程（推荐）：`git push -u origin <分支名>`
> - 暂不推送，改动只保留在本地分支

用户选"推送"后执行 push；选"暂不推送"则跳过，并在后续报告中说明该分支仅存在于本地。

**"同意推送"只认显式选择**：只有用户选择了"推送"或"创建 PR"选项才算同意。用户说"完成""好的""你看着办"都不算；拿不准时就再问一次。

## 决策点 3：是否合并回主干（开发完成时，必问）

**完成判定**（全部满足才算完成，才进入询问）：

- 需求功能已实现；
- 可行时测试已通过（仓库有测试就跑）；
- 改动已提交，工作区干净（`git status` 确认）。

满足后，**必须用 ask_user_question 询问**：

> **开发完成（分支 `<分支名>` 已提交）。是否合并回主干？**
> - 合并到主干并删除该分支（推荐）
> - 合并到主干但保留分支
> - 创建 PR（仅在存在远程时提供此选项）
> - 暂不合并

按用户选择执行：

### 合并到主干（本地）

1. 确认工作区干净（有残留改动先提交或 stash）。
2. `git switch <主干>`（旧版 `git checkout <主干>`）。
3. 有远程 → 先 `git fetch origin` 再 `git pull --ff-only`（或 `git merge --ff-only origin/<主干>`）把主干更新到最新；失败说明本地主干落后或有分叉，报告给用户，不要擅自 rebase 或强推。
4. `git merge --no-ff <分支>`。
5. 合并后如有测试，跑一遍确认。
6. 按用户选择删除分支：`git branch -d <分支>`（-d 在分支未合并时会拒绝，安全）。
7. 若需要把合并结果同步到远程（`git push origin <主干>`），这同样是一次 push——**先按「决策点 2」询问用户**，不要顺手推送。

### 创建 PR（用户选择且存在远程时）

- 创建 PR 需要先把分支推送到远程——用户选择"创建 PR"选项即视为同意推送该分支，可先 `git push -u origin <分支>` 再建 PR，无需就 push 单独再问一次（同一次选择里已包含同意）。
- 若装了 GitHub CLI：`gh pr create`，附上需求描述与测试说明；
- 否则先 `git push -u origin <分支>`，再给出在远程仓库页面创建 PR 的指引，把链接给用户。

### 暂不合并

- 告知用户分支仍保留：`git switch <分支>` 可继续开发，之后可随时再问是否推送、是否合并。

## 合并冲突处理

- 出现冲突时**不要擅自选择破坏性方案**（如 `git checkout --ours` 全量覆盖）。
- 报告冲突文件清单（`git status` 中 unmerged 列表），说明每个文件冲突的大致内容，与用户确认解决策略（保留哪边 / 手动合并）。
- 解决后 `git add <文件>`，完成 merge commit（或按用户偏好的 rebase 方式）。

## 安全红线（破坏性操作必须先问）

以下操作执行前**必须**征得用户明确同意：

- `git reset --hard`（丢弃改动）
- `git push --force` / `--force-with-lease`（覆盖远程历史）
- `git branch -D`（强制删除未合并分支）
- `git rebase` 改写已推送历史
- 删除/覆盖用户未提交的工作

## 边界情况速查

| 情况 | 处理 |
|---|---|
| 不是 git 仓库 | 告知并询问是否 `git init` |
| 工作区有未提交改动 | 询问先提交还是 stash 再开分支 |
| detached HEAD | 提示并先切回主干 |
| 已在特性分支 | 说明并继续，不重复询问建分支 |
| 主干名是 master 而非 main | 自动检测（见下），不要假设 |
| 没有远程 | 跳过 push 和 PR，只做本地合并 |
| 需要 push（特性分支或主干） | **先走决策点 2 询问用户**，显式同意后才执行 |
| 用户选择"创建 PR" | 视为已同意推送该分支，直接推送并建 PR |
| push / merge 失败 | 停止并报告原因，不盲目重试 |
| 用户明确拒绝 / 跳过 git | 尊重，之后不再反复询问 |
| 纯问答、只读分析 | 不触发本工作流 |

## 命令速查

```bash
git rev-parse --is-inside-work-tree         # 是否 git 仓库
git branch --show-current                   # 当前分支（空 = detached HEAD）
git status --short                          # 工作区状态
git remote -v                               # 查看是否配置了远程
git switch -c feat/xxx                      # 创建并切换分支
git switch main                             # 切回主干
git log --oneline -10                       # 看仓库提交风格
git add <文件> && git commit -m "feat: ..."  # 本地提交（无需询问）
git push -u origin <分支>                    # 推送（必须先经决策点 2 询问）
git fetch origin && git pull --ff-only      # 更新主干（有远程时）
git merge --no-ff <分支>                     # 合并回主干
git branch -d <分支>                         # 删除已合并分支
```

**主干检测**（不要假设是 main）：

```bash
git symbolic-ref refs/remotes/origin/HEAD --short 2>/dev/null \
  || git config --get init.defaultBranch 2>/dev/null \
  || echo main
```

**分支名 slug 生成**：需求摘要 → 小写 → 非字母数字转 `-` → 压缩连续 `-` → 截断到 40 字符左右。例：「修复登录时密码错误的空指针」→ `fix/login-npe`。

## 如何询问

- 优先使用 `ask_user_question` 工具（若当前会话有该工具）：给每个问题一个稳定 id，推荐项放第一并标注"推荐"。
- 若没有该工具：用普通文本把问题和选项列出来，**等待用户回复后再继续**，不要自问自答。
